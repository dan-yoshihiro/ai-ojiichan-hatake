# Cloudflare でアクセスの8割が404だったとき、サイトの不具合を疑う前に確かめること：自分を除く設定が1か月切れていた記録

*最終更新: 2026-11-14 / 観測: 2026-11-14 時点の直近7日・30日・60日*

> **TL;DR:** Cloudflare の Account analytics で、直近7日の4xx（404 などのエラー応答）が83.68%になっていました。サイトが壊れたのかと思いましたが、中身は `/.env` や `/.aws/credentials` を探して回るボットで、1つの IP だけで全体の64%でした。404 は正しい応答です。調べる途中で、自分のアクセスを除く設定が、プロバイダの IP 変更で約1か月切れていたことも分かりました。直近30日の日本の閲覧32件のうち19件が自分でした。参照元が付かない経路からの読者を数えるために、外に貼るリンクへ印（`utm_source`）を付ける形にしました。

Cloudflare Pages でサイトを運用していて、ダッシュボードのエラー率や国別の数字に驚いた人向けです。前の記録[「人間」4,165件を数え直したら35%が機械だった](/cloudflare-bot-detection)の続きで、そこで作った D1 のアクセスログをそのまま使っています。

## 4xx が8割でも、先にボットの探索を疑う

4xx（404 などの「見つからない・拒否した」応答）が8割を超えていても、サイトの不具合とは限りません。このサイトでは、増えた分のほとんどが、秘密の設定ファイルを探して回るボットへの 404 でした。

最初に見たのは Account analytics です。直近7日でリクエスト3.57k、そのうち4xx が2.98k（83.68%）。国別ではウクライナが一番上でした。心当たりはありません。

Account analytics と下の Logs では集計の仕方が違い、4xx の合計は一致しません（Logs で4xx を足すと3,008件）。以降の件数は Logs のものです。

Observability の Logs（データセットは HTTP requests）で、同じ7日間を応答コード別に分けるとこうなりました。

| 応答 | 件数 | 割合 |
|---|---:|---:|
| 404 Not Found | 2,871 | 80% |
| 200 OK | 512 | 14% |
| 403 Forbidden | 123 | 3% |
| 301 Moved Permanently | 71 | 2% |

送信元 IP で分けると、1つの IP だけで2,303件（64%）ありました。User-Agent（ブラウザや道具が名乗る名前）は `curl/8.6.0` が778件（22%）で一番多く、ブラウザではありません。

パス別に見ると、記事以外ではこれが並びました。

- `/.env.production` 50件
- `/.env` 41件
- `/.env.local` 38件
- `/env/.env` 35件
- `/.composer/auth.json` 34件
- `/.env.backup` 33件

ほかに `/.aws/credentials`、`/.docker/config.json`、`/wp-config.php` もありました。どれも、置き忘れた秘密の設定ファイルを拾いに来るスキャナの定番です。

このサイトは静的なファイルと Pages Functions だけで動いていて、こうしたファイルは公開していません。だから 404 で返っているのは正しい動きです。`/wp-config.php` などの 403 は、Cloudflare 側が止めたものです。Logs の集計で「Mitigated by Cloudflare」が、403 と同じ123件でした。このサイトのコードは、探索とみなしたパスに 403 ではなく 404 を返しています。

確かめるのは1点だけです。探されているファイルが、公開しているファイルの中に本当に無いか。いちばん確実なのは、探されている URL を自分でも開いて、404 が返るのを見ることです。

ファイルの置き場所からも確かめられますが、見る場所はデプロイのしかたで変わります。GitHub 連携でデプロイしているなら、配信されるのはリポジトリにあるものです。`git ls-files` に出てこなければ、外からも取れません。

`wrangler pages deploy .` で手元のフォルダをそのまま上げている場合は、`.gitignore` が効きません。外したいファイルは `.assetsignore` に並べます。

このサイトの `.assetsignore` を見ると、`.env` と `.dev.vars` が入っていませんでした。手元にそうしたファイルは無く、普段のデプロイは GitHub 連携なので漏れてはいません。それでも、手元から上げた日に漏れないよう、2つを足しました。

## pages.dev でも、Logs でリクエストを1件ずつ見られる

前の記録で「pages.dev では見られない」と書いた User-Agent は、いまは Observability の Logs で、パス・送信元 IP・国と一緒に1件ずつ見られます（2026年11月14日に確認。期間は最長で直近30日）。上の表はすべてここから作りました。ASN（接続元のネットワークの番号）は見当たりませんでした。逆に `/.env` のような Functions を通らないパスは D1 に残らないので、狙われたパスは Logs、人かどうかの見分けは D1 と使い分けています。

## 自分を除く設定は、プロバイダの IP 変更で黙って切れる

自分の閲覧を読者から除く設定は、登録した IP が変わると何も言わずに効かなくなります。このサイトでは約1か月切れていて、直近30日の日本の読者の閲覧32件のうち19件が自分でした。

前の記録で、自分の IP をハッシュにして `owner_ips` という表に登録し、集計から外すようにしました。IP が変わるたびに足していて、登録は4件になっていました。

気づいたきっかけは、自分のブラウザでトップページを開いて確かめたことです。その1件が、読者の側に記録されていました。たどると、この回線が最初に記録されたのは10月12日で、11月14日までに39件が記録され、どれも読者として数えられていました。

この回線を5件目として登録すると、直近30日の日本の数字はこう変わりました。差の19件が、39件のうち、この集計の範囲（直近30日・日本・記事などの本文）に入っていた分です。

| 直近30日・日本 | 登録前 | 登録後 |
|---|---:|---:|
| 読者として数えた閲覧 | 32 | 13 |

登録は、過去の分にもさかのぼって効きます。集計のたびに `owner_ips` と突き合わせるビュー（`access_logs_classified`。前の記録で作った、判定を集計時にやり直す仕組み）にしていたからです。直した日より前の分からも、自分の閲覧が除かれました。

防ぎ方として、自分でサイトを開いた直後に、最新の行が運営者として数えられているかを見ることにしました。

```sql
SELECT timestamp, url_path, is_owner
FROM access_logs_classified
ORDER BY timestamp DESC
LIMIT 3;
```

自分が開いたはずの行の `is_owner` が0なら、IP が変わっています。

## 自分とボットを除くと、日本からの読者は IP 10個ほどだった

自分とボットを除くと、外から来た読者は少数でした。直近30日で、日本から読者として数えた閲覧は13件、IP は10個です。IP の数は人数と同じではありません。同じ回線の複数人は1つに、回線を変えた1人は複数に数えられます。

日本以外にも「人間らしい」アクセスはありましたが、多くは1つの IP が20ページ以上を順に回る形でした。たとえばドイツの1つの IP から、198件・24ページです。User-Agent は普通のブラウザを名乗っていても、1つの IP がサイトの全ページを順に開くのは人の読み方ではないので、読者には数えていません。

参照元（どのページのリンクから来たか）も見ました。

- Google の検索結果から来た行は、30日で十数件ありました。ほぼすべて Cloudflare のネットワークから来ていて、検索語はこのサイトの名前でした。同じ分のうちに何ページも開き、同じ時刻には AI bot と判定された行も並んでいます。人ではなく、名前で検索して巡回する道具だと見ています。
- X（`t.co`・`x.com`）からの参照元は、記録を始めた2026年5月6日から一度もありませんでした。

X の0件は、「X から誰も来ていない」とは言い切れません。X のアプリ内ブラウザは参照元を送らないことが多く、その場合はブックマークや直接入力と同じ「参照元なし」に混ざります。参照元だけを見ていると、SNS のアプリから来た人の多くを数え漏らします。

## 参照元が付かない経路は、リンクに utm_source を付けて数える

参照元が付かない経路からの読者は、外に貼るリンクの URL に印を付けておけば数えられます。印には `utm_source` というパラメータを使いました。`?utm_source=note_article` のように、リンクを貼った場所を URL に書き込んでおく目印で、ページの表示には影響しません。

入口は note にしました。2026年11月14日に、note の記事5本からこのサイトへのリンクを `?utm_source=note_article` 付きにしています。X には貼っていません。X のフォロワーは家庭菜園が目当ての人が中心で、AI に投稿を任せた運用の記録には誘わないと決めたからです。

D1 には `url_path` をクエリ文字列ごと記録しているので、`utm_source=` の値を取り出せば入口ごとに数えられます。

```sql
CASE
  WHEN INSTR(url_path, 'utm_source=') > 0 THEN
    SUBSTR(
      SUBSTR(url_path, INSTR(url_path, 'utm_source=') + 11),
      1,
      COALESCE(
        NULLIF(INSTR(SUBSTR(url_path, INSTR(url_path, 'utm_source=') + 11), '&'), 0) - 1,
        LENGTH(url_path)
      )
    )
END AS utm_source
```

`utm_source` が無い行は、参照元のホストで分け、それも無ければ「参照元なし」にします。運営者・AI bot・その他の機械・200以外の応答は、前の記録と同じ条件で外しています。

11月14日の時点で、`utm_source` 付きの閲覧は0件です。ここからの増え方で、note の入口が効いたかを確かめます。

## 同じことを確かめる手順

1. エラー率が上がったら、Observability の Logs で応答コードとパスを分ける。`/.env` や `/wp-config.php` が並んでいれば、探索の 404 で正常。
2. 探されている URL を自分でも開いて 404 を確かめる。手元のフォルダを直接デプロイしているなら、`.assetsignore` に `.env` と `.dev.vars` が入っているかも見る。
3. 送信元 IP と User-Agent で分け、少数の IP や `curl` に偏っていないか見る。
4. 自分でサイトを開き、その行が運営者として除かれているか確かめる。外れていたら、新しい IP を登録する。
5. 外に貼るリンクには `?utm_source=` を付け、貼った場所ごとに値を変える。参照元が付かない経路でも数えられる。

## 分かったことと、まだ分からないこと

分かったことです。

- 直近7日の4xx 83.68%は、秘密の設定ファイルを探すボットへの応答で、1つの IP が64%を占めていた。サイトの不具合ではなかった。
- pages.dev でも、Observability の Logs でパス・送信元 IP・国・User-Agent をリクエストごとに見られる。ASN は見当たらなかった。
- 自分を除く設定が、IP の変更で10月12日から切れていた。直近30日の日本の閲覧32件のうち19件が自分だった。
- 外から来た読者は、直近30日の日本で閲覧13件・IP 10個。X からの参照元は、5月6日から0件。

まだ分からないことです。

- note の入口からどれだけ人が来るか。2〜4週間後に、この記事に追記します。
- 参照元なしの中に、SNS のアプリから来た人がどれだけ混ざっているか。

ボットを除き、自分を除いて、残ったのが13件です。ただ、自分を除く設定は1か月黙って切れていました。いまの13件にも、まだ気づいていない自分や機械が混ざっているかもしれません。数え方を直すたびに読者が減っていくこの作業が、どこで終わるのかは、まだ分かりません。
